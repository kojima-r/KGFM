# benchmark_scorer — スコア関数とヘッド結線の比較

`benchmarks/` が「どのエンコーダ・どのヘッド型か」を問うのに対し、ここは
その**下流にある 2 つの選択**を問います。エンコーダが 3 本のベクトルを出した
あとで、

1. **h, r, t は同じヘッドを通すべきか**（`head_mode`）
2. **3 本を何で 1 つのスコアにまとめるか**（`scorer`）

どちらもこのリポジトリでは長らく選択肢ですらなく、`(shared, DistMult)` に
固定されていました。

| | benchmarks/ | benchmark_scaling/ | **benchmark_scorer/** |
|---|---|---|---|
| 問い | どの構成が強いか | 容量を増やすと | **スコア関数とヘッド結線** |
| sweep 軸 | encoders × heads × freezes | モデルサイズ | **head_modes × scorers** |
| 出力 | `table.md` | `scaling_table.md` | `scorer_table.md` / `scorer_report.html` |

```bash
bash benchmark_scorer/run_scorer_smoke.sh   # 8 セル、数分。まず通しを確認
bash benchmark_scorer/run_scorer.sh         # 本番 8 セル、約 3 時間
```

## 1. ヘッド結線 (`--head-mode`)

| モード | 中身 |
|---|---|
| `shared`（既定） | h, r, t を**同じヘッド**に通す。これまでの唯一の挙動 |
| `separate` | h, r, t に**それぞれ専用のヘッド**。ヘッドのパラメータは 3 倍 |

**エンコーダの forward は両モードとも 1 回のままです。** `encode_triple` は
h+r+t を 3B 本の 1 バッチにまとめて 1 回だけエンコーダに通し（transformer で
3 倍の高速化）、ヘッドはそのあとスライスごとに適用します。したがって
`separate` の追加コストはヘッドのパラメータと小さな行列積 3 つで、
エンコーダ 3 パスではありません。

**`shared` が既定なのは惰性ではありません。** `hr @ pool.t()` が意味を持つの
は、候補プールが tail として 1 度だけエンコードされ、クエリが**同じ空間**に
いるからです。`separate` にすると「同じ文字列でも h として射影したものと
t として射影したものは別ベクトル」になるので、`encode()` に **role 引数**が
必要になります。既定は `role="t"` — 一括エンコードの呼び出し元
（`eval.build_candidate_pool` / `build_filter_index`）はどれも候補 *tail* の
バンクを作っているためです。ここを間違えると、**もっともらしい数値のまま
間違ったヘッドで射影した tail に対してスコアを付けます**。

**比較で必ず添えること: `separate` はヘッド容量が 3 倍です。** 勝っても
「役割ごとの射影という帰納バイアスが正しい」と「単にパラメータが多い」の
両方が生きた説明で、面白いのは前者だけです。レポートは全表に**ヘッドの
パラメータ数を併記**し、要約でもこの点を明示します。

## 2. スコア関数 (`--scorer`)

| scorer | 式 | 種別 | 対称性 |
|---|---|---|---|
| `distmult`（既定） | `Σ_d h_d·r_d·t_d` | 内積 | **対称**（h と t を入れ替えても同じ） |
| `complex` | `Re<h, r, conj(t)>` | 内積 | 非対称 |
| `transe` | `-‖h + r - t‖₂` | 距離 | 非対称 |
| `rotate` | `-‖h ∘ r̂ - t‖`（r の各複素成分を単位長に正規化） | 距離 | 非対称 |

**DistMult が対称なのは実際の制約です** — 「A が B を阻害する」を表現すると
「B が A を阻害する」も同じスコアになります。ComplEx はベクトルの前半・後半を
複素数の実部・虚部として読むことでこれを外します（実測で検証済み:
DistMult は `|s(h,r,t) − s(t,r,h)| = 0`、他の 3 つは非ゼロ）。

### インタフェースは数式ではなく評価のコストが決めています

候補プールに対するランキングは `[B]` 個のクエリを `[P]` 個の tail に対して
スコア付けます。P は 6,000〜2,000,000 です。`[B, P, D]` を materialize して
任意の `f(h,r,t)` を要素ごとに適用するのは**不可能**なので、すべての scorer は

```
q = query(h, r)              # [B, Dq]  t を含まない部分
S = score_against(q, T)      # [B, P]   バンクに対する 1 回の融合演算
```

の 2 段形で書けなければなりません。これが `hr @ pool.t()` を成立させている
条件です。**この形に書けない scorer はここに入れません** — 関係ごとの行列を
持つ完全な双線形 `h^T W_r t` などは、200 万 tail の評価を黙って OOM に
変えてしまいます。

満たす形は 2 系統です。

- **内積系**（`distmult` / `complex`）: `S = q @ T.t()`
- **距離系**（`transe` / `rotate`）: `S = -‖q - T‖`。`torch.cdist` が
  `[B,P,D]` に展開せず全行列を出すので、コストは行列積と同オーダーです

`score_diag` を別に持つのは、真の tail が行ごとのスコアだからです（全行列の
対角を取るのは二次の無駄）。**この 2 経路は最下位ビットで食い違います** —
`q @ T.t()` と `(q*t).sum()` は累積順序が違うため — が、それは
`eval._ranks_with_ties` が許容誤差を持つ理由としてすでに記録されている
約 1e-7 の系統差そのものです。

### 複素系は偶数次元が必要です

`complex` と `rotate` はベクトルを D/2 個の複素数として読むので、スコア次元が
奇数だと成立しません。**黙って切り捨てず、構築時にエラーにします。**

## 実装の要点

- **`kgfm/scorers.py`** — レジストリ。全 scorer が**パラメータを持ちません**
  （固定の式）。これが「scorer を替えてもパラメータ数が変わらない」ことを
  保証し、差をスコア関数に帰属させられる理由です。
- **`DistMultScorer` の名前は残しています。** チェックポイントの再構築経路が
  この名前を書いており、`state_dict` のキーも読み込みに効くためです。
  既定（`shared` / `distmult`）では `proj.*` キーを含めて以前と同一の
  モジュールになります。新しいコード用の別名が `TripleScorer` です。
- **既存チェックポイントは読めます。** 4 つの再構築経路
  （`eval.py` / `bench/cell.py` / `hf.py`）はいずれも
  `cfg.get("head_mode", DEFAULT_HEAD_MODE)` で読むので、当該キーを持たない
  古いチェックポイントは shared / distmult として再構築されます — 実際に
  そう学習されたものです。
- **検証済み**: 既存チェックポイントを再スコアして MRR が
  `0.3101983704` → `0.3101983741` と有効数字 8 桁一致（float32 の累積順序
  差のみ）。リファクタは DistMult の数値を変えていません。

## 同梱 config

| ファイル | セル | 予算 / セル | 所要 |
|---|---|---|---|
| `config_scorer_small.yaml` | 8 | 12,800 例 | 数分（通し確認） |
| `config_scorer.yaml` | 8 | 10,240,000 例 | 約 3 時間 |

固定するもの（動かすと交絡します）:

- **encoder: ngram** — 最強だからではなく（28 セル比較で 5 位）、
  ~17,000 ex/s で回るからです。scorer を唯一の変数にしたいのに、
  fine-tune した transformer を挟むと軸と指標の間に 1000 倍のパラメータが
  入り、8 セルで数日かかります。
- **proj_dim: 256**（偶数）、**batch_size: 512 全セル共通**（B-1 が負例数
  そのもの）、**loss: contrastive 全セル共通**。

## いちばん重要な留保: loss は scorer に対して中立ではありません

`contrastive` はクエリと tail を L2 正規化します。**内積系にとっては行ごとの
正のスケーリング**なので順位を変えられません（DistMult / ComplEx の
ランキングは不変）。しかし**距離系にとっては点を動かす**ので、幾何そのものが
変わります。TransE と RotatE は本来、生スコアに対する margin 系の損失で
学習するものです。

8 セルで 1 つの loss に固定しているのは **scorer を唯一の変数にするため**
ですが、それは距離系にとってハンデです。したがって transe / rotate の数値は
**「この loss の下での値」**であって「出しうる最良の値」ではありません。
レポートもこの注意を結果の隣に印字します。

自然な追試は同じ config を `--loss self_adversarial --margin 9` で回すこと
です。ただしそれは**固定するものが変わる**ので、セルごとの調整ではなく
2 本目の run として扱ってください。

## 本番の結果

`results/chembl/20260909T035740Z_scorer`（8 セル、`ngram`、20,000 step、
B=512、proj_dim 256、`contrastive`、各セル約 17 分）。表の MRR は
**filtered** プロトコルの値です。

### filtered MRR

| head_mode | distmult | complex | transe | rotate |
|---|---|---|---|---|
| shared | **0.4737** | 0.4707 | 0.3273 | 0.3845 |
| separate | 0.4566 | 0.4636 | 0.3765 | 0.4215 |

### best valid loss（低いほど良い）

| head_mode | distmult | complex | transe | rotate |
|---|---|---|---|---|
| shared | 3.8972 | 3.9358 | 3.9130 | 3.9681 |
| separate | 3.6451 | **3.6253** | 3.7525 | 3.7307 |

**最良セルが 2 つの指標で一致しません** — MRR は `shared`+`distmult`、loss は
`separate`+`complex` を選びます。これは他の 2 つのスタディが記録している
「loss の天井」と同じ問題で、どちらが正しいかではなく、**loss だけで
head_mode を決めてはいけない**ということです。

### 周辺平均は head_mode について誤読を招きます

| 軸 | filtered MRR | best valid loss |
|---|---|---|
| `shared` | 0.4141 | 3.9285 |
| `separate` | **0.4296** | **3.6884** |
| `distmult` | 0.4652 | 3.7711 |
| `complex` | **0.4671** | **3.7806** |
| `transe` | 0.3519 | 3.8327 |
| `rotate` | 0.4030 | 3.8494 |

周辺平均は `separate` の勝ち（+0.0155）に見えます。**しかしこれは符号の
違う 2 つを平均した数字です。**

| scorer | 種別 | separate − shared (MRR) |
|---|---|---|
| distmult | 内積 | **−0.0171** |
| complex | 内積 | **−0.0071** |
| transe | 距離 | **+0.0492** |
| rotate | 距離 | **+0.0370** |

**内積系は `shared` を、距離系は `separate` を好みます。** これは
pooled / filtered の**両プロトコルで 4 セルとも同じ向き**に出るので、
プロトコル選択の産物ではありません。head_mode に単一の答えはなく、
scorer との交互作用がすべてです — だからこの表を平坦にはできません。

直観的には、距離系は h と t を**同じ空間**に置いて `‖h+r−t‖` を測るため、
役割ごとに別の射影を与えると h 側だけを動かす自由度が生まれます。内積系は
`hr @ pool.t()` の形がまさに共有空間を前提にしているので、分けると失います。

### そのほか読み取れること

- **ComplEx は DistMult に勝っていません**（周辺 0.4671 vs 0.4652、shared で
  0.4707 vs 0.4737）。差は 0.002–0.005 で、この統計では区別できません。
  DistMult の対称性は実際の制約ですが、**ChEMBL のこの設定では効いていません**。
- **内積系 4 セルが上位 4 位を占めます**（両プロトコルで）。距離系の劣位は
  大きく明確ですが、これは上の留保どおり `contrastive` の下での値です。
- **`separate` は loss では 4 つの scorer すべてで勝ちます**（0.16–0.31 nats）。
  ヘッドパラメータが 3 倍（65,792 → 197,376）であることと整合的で、
  しかも内積系ではランキングに**変換されていません**。容量が loss を下げても
  順位を改善しない例です。
- **学習時間はほぼ一定**（1,002–1,095 秒）なので、どの差も計算量の差では
  ありません。
- 分解能の目安: validation は 8 バッチ × 80 点の最小値なので、
  model-size スタディと同じく **~0.05 nats 未満の loss 差は読めません**。
  `separate` vs `shared`（0.16–0.31）は読めますが、同一モード内の
  distmult vs complex（0.039）は読めません。

### 結論

このリポジトリの既定である `(shared, DistMult)` は、**MRR で見るかぎり
8 セル中の最良**でした。変えるべき理由は今回の範囲では見つかっていません。
ただしそれは「DistMult が最良のスコア関数だから」ではなく、
**ComplEx と区別できなかったから**であり、距離系については
`contrastive` 以外の loss で追試するまで判断できません。

## レポートの中身

`scorer_report.html` / `scorer_table.md` / `scorer_points.json` が実行
ディレクトリに出ます。

| セクション | 見方 |
|---|---|
| Experiment settings | 何を固定して何を振ったか |
| **caveats** | ヘッド容量 3 倍と loss の非中立性。数値より先に読む |
| 指標ごとの**グリッド**（MRR / Hit@1 / Hit@10 / nDCG / best valid loss） | 2 軸の交差表。最良セルに `*` |
| **周辺平均** | もう一方の軸で平均した値 = 「その軸はそもそも効くのか」 |
| Per cell | ヘッドのパラメータ数・種別（内積/距離）・学習時間つき |
| 学習曲線 | validation loss と MRR、セルごと |

`kgfm report` の平坦な表ではなくこの形にしたのは、行が「別の手法」ではなく
**2 次元のグリッド**だからです。平坦な表では「差を説明しているのはどちらの
軸か」が読めません。
