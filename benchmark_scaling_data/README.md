# benchmark_scaling_data — データ量に対するスケーリング則の測定

`benchmark_scaling/` と同じパイプラインで、**軸だけが違う**実験です。
あちらがモデルサイズ、こちらが**ユニークな学習データ量**です。

| | benchmark_scaling/ | benchmark_scaling_data/ |
|---|---|---|
| 問い | 容量を増やすと損失はどう下がるか | **データ量**を増やすと損失はどう下がるか |
| sweep 軸 | モデルサイズ (`encoders`) | **`data_sizes`**（= `max_rows_per_file`） |
| 固定するもの | データ（実質無限）・step 数 | **モデル・step 数・バッチサイズ** |
| フィットの形 | `L = L∞ + a·C^b`（C = 計算量） | `L = L∞ + a·D^b`（D = ユニーク行数） |
| 1 セルの寄与 | **曲線**（軌跡が計算量軸を張る） | **1 点**（best loss。D はセルの属性） |
| 主な出力 | `scaling_table.md` / `scaling_report.html` | `data_scaling_table.md` / `data_scaling_report.html` |
| 出力先 | `benchmark_scaling/results/chembl/` | `benchmark_scaling_data/results/chembl/` |

学習は `kgfm bench run` がそのまま担当します。**データ軸専用の学習コードは
ありません** — `report_data.py` が既存の `cell_*.log` を (D, 損失) 座標に
読み替えるだけなので、終わった run に後から実行できます。

## 使い方

```bash
bash benchmark_scaling_data/run_data_smoke.sh    # 数分。まずこれで通しを確認
bash benchmark_scaling_data/run_data_ngram.sh    # ngram 8 セル（約 2 時間）
bash benchmark_scaling_data/run_data_scratch.sh  # ★ 本番: 41M transformer 8 セル（約 11 時間）
bash benchmark_scaling_data/resume_data.sh latest
```

各スクリプトは 3 コマンドです。

```bash
kgfm bench run --config benchmark_scaling_data/config_data_scratch.yaml
kgfm report --out-dir latest --results-root benchmark_scaling_data/results/chembl
python benchmark_scaling_data/report_data.py --out-dir latest
```

`report_data.py` が `kgfm scaling` のサブコマンドではなく独立したスクリプトな
のは、プロットの形が根本的に違うからです（後述「なぜ 1 セル 1 点なのか」）。
フィット関数（`fit_power_law` / `fit_saturating`）・配色（viridis）・チャート
バックエンドは `kgfm/scaling/` からそのまま再利用しています。

## 何を「データ量」と呼んでいるか

**`max_rows_per_file` を振ります。** ユニークな学習行数 D は

```
D = Σ_f min(rows(f), max_rows_per_file)
```

で、レポートは**実測で数えます**（`kgfm.data.count_rows`。`(パス, サイズ,
mtime)` でディスクにキャッシュされるので 2 回目以降は即時）。`85 × cap` で
掛け算しないのは、`list_chembl/train.txt` の 85 ファイルのうち **15 個が
60 万行未満**（最小 253 行）で、上の方の cap では最大 10% ずれるからです。

### なぜ「ファイル数を減らす」ではないのか

ChEMBL の TSV は activity ID で分割されているので **1 ファイル = 1 つの
エンティティ集団**です。ファイルを減らすと**データ量と集団の多様性が同時に
動いて**しまい、これは別の軸です（`benchmarks/README.md`「2 台目の GPU が
増やすのは『データ量』より『ファイル多様性』」）。`max_rows_per_file` は
各ファイルを独立に切るので、**85 ファイル全部がラウンドロビンに残ったまま、
1 集団あたりの行数だけが変わります**。動く変数を D だけにするための選択です。

### なぜそもそも上限をかける必要があるのか

**上限なしではデータ量の効果は原理的に観測できません。** train プールは
674,265,105 行あり、本番の予算は 614 万例（`scratch` config）です。つまり
**0.009 エポック**で、同じ行が二度出てきません。この状態では
「データを増やす」と「step を増やす」が同じ変数で、有限データ効果
（過学習）は定義上起こりません。

上限をかけるとプールが有限になり、学習ループが

```python
while step < cfg.max_steps:
    for batch in loader:      # ← 尽きるとここで新しいイテレータが作られる
```

の構造をしているため、**同じ行を何度も見に行きます**。この繰り返しが
測定対象そのものです（バグではありません）。実測で確認済み: 200 行に
制限したデータセットは 1 パス 200 行を返し、2 周目は 1 周目と完全に同一の
順序で同じ 200 行を返します。

> **注意: 各エポックの順序は同一です。** `StreamingTripleDataset` は
> イテレータを作るたびに `random.Random(seed + worker_id)` を張り直すので、
> ファイル順もシャッフルバッファも毎周同じになります。したがって
> 「同じデータの繰り返し」ではありますが、「毎周シャッフルし直す」通常の
> 実装とは違います。バッチ構成が毎周同一なので in-batch 負例も同一で、
> 過学習はやや起きやすい側に寄る可能性があります。D の効果を消す方向では
> ないので測定は成立しますが、絶対値を他所と比べるときは意識してください。

## 設計: なぜ 1 セル 1 点なのか

`benchmark_scaling/` では 1 セルが**曲線**を寄与します。1 回の学習が自分より
小さい計算量予算をすべて通過するので、軌跡そのものが計算量軸を張るからです。

データ軸ではそうなりません。**D はセルの属性**で、そのセルのどの validation
点も同じ D を持ちます。全点をフィットに入れると「どのセルが何回検証されたか」
で重み付けした縦方向の塊を引くことになります。そこで

- **フィットは 1 セル 1 点**（そのセルの **best validation loss**）
- **軌跡は別の目的に使う** — 小さい D のセルが途中で**上向きに折れる**ことを
  見せるため

という分担にしています。

**best を採るのは、有限データの run が過学習するからです。** 最終値は
「最適点をどれだけ通り過ぎたか」を測ってしまい、最小値が「その量のデータで
何が買えるか」を測ります。これは `benchmark_scaling/` の
「early stopping を入れてはいけない」と矛盾しません — あちらは
**停止規則**が二相性の谷を切り落とす話で、こちらは完走した run から
事後に最良点を読むだけです。何も止めていません。

## レポートの中身

`data_scaling_report.html` / `data_scaling_table.md` / `data_scaling_points.json`
が実行ディレクトリに出ます。

| セクション | 見方 |
|---|---|
| **The law: best loss vs unique data** | 主役。log-log で 1 セル 1 点 + フィット曲線（x = 行数） |
| フィット表（2 種） | `a·D^b` と床つき `L∞ + a·D^b` を必ず両方出す |
| **regime note** | **どのセルが 1 パス以上回ったか**。ここを最初に読む |
| Same cells, ranking-error axis | 同じ点を `1 − MRR` で。loss 軸の天井を回避 |
| **The law in token units** | **x = ユニークトークン数**。スケーリング則論文の慣習の形 |
| Ranking error vs unique tokens | 同上を `1 − MRR` で |
| **loss vs training tokens processed** | x = 累積処理トークン（繰り返し込み）。Kaplan 流の図 |
| **Trajectories** | validation loss vs step、色 = D。小さい D が折れ返るのが見える |
| 同じ軌跡 vs パス数 | x 軸を「自分のプールを何周したか」に。最小値が揃うなら最適点は再利用回数で決まる |
| Generalisation gap vs D | valid − train。D が小さいほど大きい = 機序の直接確認 |
| Per cell / Where each minimum landed | 各セルの best が内点か末端か（末端なら下限値） |

### regime note を最初に読む理由

**1 パスに届いていないセルでは D は律速要因ではありません。** step 予算が
律速していて、そのセルは「データ量」ではなく「計算量」を測っています。
そういう点を通してフィットすると、平坦な尾に引きずられて指数が浅く出ます
（`benchmark_scaling/` の「2 パラメータの冪則は曲がれない」と同じ現象）。

レポートは**その run の実際の値から毎回再計算して**、何セルが繰り返し領域に
入ったか・入らなかったセルはどれかを明記します。同梱 config では
上限なしのセルを**1 つだけ**入れてあり、これは床 `L∞` を同定するための
右端アンカーです（複数入れると平坦な尾になって指数を潰します）。

### トークン軸（スケーリング則論文の慣習）

行数 `D` はこの研究の**ノブそのもの**（`max_rows_per_file` は行を数える）
ですが、スケーリング則の文献は**トークン数**を横軸に取ります。両方出します。

**ユニークトークン数は実測から出します。** トレーナーが
`tokens=`（エンコーダを通った padded トークンの累積）をログに出しているので、

```
tokens/example = 累積トークン / (step × global_batch_size)
ユニークトークン = ユニーク行数 × tokens/example
```

で求めます。`3 × max_length` から導出はしません — tokenizer はバッチ内最長に
パディングするので実際のレートは上限よりずっと低く、しかもセルごとに違います。

**行数軸の単なる貼り替えではありません。** `max_rows_per_file` は各ファイルの
先頭 D 行を取るので、セルごとに読む場所が違い、実測 tokens/example は
240〜303 の幅を持ちます（下表）。ただし比例に近いので**指数はほぼ同じ**に
なります（scratch-medium で行数軸 −0.0280 に対しトークン軸 −0.0277）。
つまりトークン軸は「別の法則」ではなく、**同じ法則を文献と比較可能な単位で
言い直したもの**です。係数だけが大きく変わります。

| 図 | x 軸 | 何を見るか |
|---|---|---|
| The law in token units | **ユニークトークン数** | データセットの大きさ。データ制約下のスケーリング則の標準形 |
| loss vs training tokens processed | **累積処理トークン数** | 実際に押し込んだ量（繰り返し込み）。全セルが同じ総量で終わるので、線の分離は「そのトークンが何種類の元データから来たか」だけで決まる |

> **`ngram` のトークンは transformer のトークンと別単位です。**
> `HashedNgramEncoder.tokens_seen` は文字 n-gram のルックアップ数を数えて
> いてサブワードトークンではありません（`kgfm/encoders.py` のコメント参照）。
> レポートは ngram の run に**単位警告を表示**します。run 内での指数は
> 有効ですが、transformer の run と x 値を並べてはいけません。

### 2 つの y 軸

`benchmark_scaling/` と同じ理由で 2 つ出します。validation loss は
in-batch 負例に対する softmax なので上が `ln(B)`、下が tail の重複で
決まる床に挟まれていて、動ける幅が狭いのです。`1 − MRR` は固定サイズの
候補プールに対する順位なので目的関数側の天井を持ちません。モデルサイズ軸では
この差が指数 −0.037 対 **−0.332** として現れました。

### モデルの選び方

**`scratch-medium` が本番**です。事前学習済みエンコーダを使うと
「ユニークな ChEMBL データ量」が「未計測の事前学習量の上に載ったデータ量」
になってしまい、軸の左端が D と無関係な理由で平坦になります。
`random_init: True`（重みを一切ダウンロードしない）はそれを外すためのもので、
`benchmark_scaling/` が同じ理由で `scratch-*` を使っているのと同じ判断です。

**`ngram` は速いので先に回す用**です。268M の EmbeddingBag は参照表なので、
小さい D を丸暗記する容量が確実にあります — この研究が到達したい領域です。
2 つの指数の差は「有限のプールを丸暗記する」と「そこから学習する」の差に
対応します。

### 学習率はセルごとに振っていません（意図的）

`config_data_scratch.yaml` は全セル `lr: 3.0e-5`（`scratch-medium` の
`benchmark_scaling/lr_probe.py` 実測最適値）で固定しています。これは
**uncapped のコーパスで測った値**なので、D が小さいセルは個別には別のレートを
好むかもしれません。それでも振らないのは、セルごとに再調整すると
**「データが少ない」と「そのレートがたまたま少ないデータに合っていた」が
交絡する**からです — モデルサイズ軸で長々と記録されているのと同じ失敗です。
1 つのレートで通すのが対照実験になります。小さい D のセルが「過学習」ではなく
「病的」に見える場合だけ、結論を出す前にプローブしてください。

## 実装: `data_sizes` は sweep 軸として追加しました

`kgfm bench` の sweep 軸は `encoders × heads × freezes` でした。データ軸は
全セルが同じ encoder なので、**そのままではセルタグが全部衝突します**。
そこで `heads` が軸になったときと同じ形で `data_sizes` を追加しました
（`kgfm/bench/config.py`）。

- セルタグは `<encoder>[_<head>][_d<size>][_frozen]`。**`_d<size>` は
  `data_sizes` を 2 つ以上振ったときだけ**付くので、既存 config のタグ
  （したがって結果 JSON のファイル名）は 1 つも変わりません
  （`benchmarks/` と `benchmark_scaling/` の全 10 config で確認済み）。
- `_d<size>` の名前は `config.data_tag()` が付けます（`d1k` / `d100k` /
  `d1m` / `dall`）。`null` は `all` になります — 「上限なし」は軸の実在する
  右端で、それを表す整数が無いためです。
- 優先順位は `defaults:` → **軸の値** → `cells: <tag>:` → CLI。軸の値が
  `defaults:` に勝つのは、それがそのセルを**そのセルたらしめている**値
  だからです。個別に上書きしたいときは `cells:` を使えます。
- `--data-sizes 100,1000,all` で CLI からも振れます。**`--max-rows-per-file`
  とは別物**です（後者は全セル共通の単一上書き）。

### トレーナー側の変更は 1 行のログだけです

```
[init] data cap: max_rows_per_file=100000 row_keep_prob=1 train_files=85
```

`cell_*.log` に D を復元する手段が他に無いためです。行数そのものを出さない
のは、それにはコーパス全体の行数カウント（105 GiB でキャッシュが空なら
約 5 分）が必要で、**すべての `kgfm train` にその代償を払わせられない**
からです。レポート側が `data.count_rows`（キャッシュ済み）で数えます。

このログ行が無い（＝この変更より前の）ログでは、レポートは D を
**「unknown」と表示して軸に載せません**。「上限なし」と扱うのは危険です —
値としては同じ `None` ですが、run について正反対のことを意味するので、
実際には制限されていた run を軸の右端に置いてしまいます。

### フィット

|---|---|---|---|---|---|---|
| valid loss | **−0.0339** | **0.980** | −0.0167 | 0.577 | 3.523, −0.1299 | 0.681 |
| 1 − MRR | **−0.0369** | **0.853** | −0.0205 | 0.609 | 0.5206, −0.2467 | 0.694 |

トークン軸（ユニークトークン数、D が効く 7 セル）: valid loss
**−0.0334**（R²=0.983）、`1 − MRR` **−0.0365**（R²=0.863）。行数軸と実質同じで、
係数だけが変わります（5.062 → 5.557）。**ただし ngram の「トークン」は
文字 n-gram のルックアップ数**なので、transformer の run と x 値を並べては
いけません（レポートも単位警告を出します）。

**引用すべきは左端の列です。** 1 パスに届かない `dall` を落とすだけで
指数が 2 倍（−0.0167 → −0.0339）、R² が 0.577 → **0.980** になります。
regime note の警告どおりで、レポートはこの制限フィットを既定の第 1 行として
出します。床つきの形（`at_boundary: false`）も併記しますが、こちらは
右端 1 点で床を決めているので参考値です。

### 過学習の機序が単調に出ています

これがこの研究の主結果です。**D が小さいほど (a) 最適点が早く来て
(b) その後の上昇が大きい**、が完全に単調です。

```
D=8.5K    最適 step   250  → その後 +1.2277 nats 悪化
D=25K     最適 step   250  → +1.1650
D=84K     最適 step   500  → +0.7142
D=247K    最適 step 2,250  → +0.2569
D=808K    最適 step 6,750  → +0.1430
D=2.4M    最適 step 10,000 → +0.0782
D=7.7M    最適 step 15,500 → +0.0980
```

「データが足りないと早く底を打って、あとは丸暗記して汎化が落ちる」という
予想どおりの挙動が、8 セル 3 decade にわたって乱れなく出ています。
軸が意図どおり機能していることの内部検証でもあります。

### 上限なしのセルだけ単調性を破ります — そして理由が特定できました

`ngram_dall`（3.8972）は `ngram_d100k`（3.6738）より **0.22 nats 悪い**です。
「データを増やすと悪くなる」と読みたくなりますが、そうではありません。

この 2 セルは **step 14,500 までビット単位で同一**です（valid loss が完全に
一致）。`max_rows_per_file: 100000` は 1 ファイルが 10 万行を出すまで何も
しないので、それまで両者はまったく同じデータを同じ順序で見ています。
分岐は **step 14,750（755 万行消費 ≒ d100k のプール 7,732,879 行）**、
つまり d100k がプールを一周し終えた瞬間です。

```
step    d100k    dall
13750   4.0145   4.0145   ← 同一
14750   4.0285   4.0713   ← d100k がラップ開始
15750   3.6955   4.0144   ← 繰り返した方が急落
19750   3.7582   4.0906
```

**同じモデル・同じ optimizer 状態・同じ 14,500 step までの履歴から分岐して、
「プールを 2 周目に入る」方が「新しいデータを読み進める」方より 0.25 nats
良かった**、という統制の取れた比較になっています。

機序はおそらく**母集団シフト**です。ChEMBL のファイルは activity ID 順なので、
ファイルを深く読むほど train の分布が valid から離れていきます
（トップレベル README「ファイルはインターリーブして読む」）。上限つきセルは
valid に合わせ込んだ分布を再訪するのに対し、上限なしセルは離れていく一方です。

**したがって `dall` は「データ量」ではなく「どこまで深く読んだか」を測って
います。** レポートの regime note も、このセルだけが 1 パスに届いていない
（0.015 パス）ことを明示します。フィットには含まれていますが、床 `L∞` を
同定するアンカーとしての役割で、単調性の判定からは外して読んでください。

### この設計の制約（結論を書くときに必ず添えること）

- **`max_rows_per_file` は各ファイルの「先頭 D 行」で、ランダム標本では
  ありません。** したがって D を増やすことは「量を増やす」と同時に
  「各ファイルをより深く読む」ことでもあり、上で見たとおりこの 2 つは
  分離できていません。ランダム標本にするには `row_keep_prob` ですが、
  それは 6.74 億行を実際に読み切る必要があり実用的ではありません。
- **小さい D の best は評価解像度で頭打ち**（脚注 1）。`eval_every` を
  下げれば指数はもう少し急になるはずです。
- ngram は 268M エントリの EmbeddingBag（参照表）なので、丸暗記の
  しやすさは実モデルと違います。次節の transformer と併読してください。

## 実測結果 2: scratch-medium（`20260905T062113Z_data_scaling_scratch`）

41.4M のランダム初期化 transformer、8 セル × 24,000 step × B=256
（= 各セル 6,144,000 例）、全セル `lr: 3.0e-5`。約 7 時間。

| セル | D（実測） | パス数 | best valid loss | @step | best 後の上昇 | best MRR |
|---|---|---|---|---|---|---|
| `d100` | 8,500 | 722.8 | 3.4253 | 500 | **+1.3760** | 0.4226 |
| `d300` | 25,421 | 241.7 | 3.2784 | 750 | **+1.7549** | 0.4310 |
| `d1k` | 83,521 | 73.6 | 3.1947 | 1,250 | +0.9631 | 0.4570 |
| `d3k` | 247,322 | 24.8 | 3.1069 | 13,000 | +0.1779 | 0.4706 |
| **`d10k`** | 807,680 | 7.6 | **2.9357** | 19,750 | +0.1117 | 0.4881 |
| `d30k` | 2,377,999 | 2.6 | 2.9496 | **24,000**¹ | +0.0000 | 0.4872 |
| `d100k` | 7,732,879 | 0.79² | 2.9469 | 22,750 | +0.0705 | **0.5102** |
| `dall` | 674,265,105 | 0.01² | 2.9297 | 22,750 | +0.0399 | 0.4863 |

¹ 最終評価点が最良 = 予算が律速。この値は下限です。
² 1 パス未満 = D ではなく step 予算が律速。フィットから除外されます。

### フィット

| y 軸 | **D が効く 6 セル** | R² | 全 8 セル | R² | 床つき (L∞, b) | R² |
|---|---|---|---|---|---|---|
| valid loss | **−0.0280** | **0.960** | −0.0140 | 0.710 | 2.927, −0.4900 **(端)** | 0.891 |
| 1 − MRR | **−0.0237** | **0.954** | −0.0123 | 0.609 | 0.4796, −0.1372 | 0.720 |

トークン軸（ユニークトークン数、D が効く 6 セル）: valid loss
**−0.0277**（R²=0.961）、`1 − MRR` **−0.0235**（R²=0.956）。こちらは
サブワードトークンなので、**文献の数値と直接比較できるのはこの行**です。
ユニークトークン数は 2.42M（D=8,500）〜 200G（上限なし）で、実測
tokens/example は 284〜303 でした。

ngram と同じく、非拘束セルを落とすと指数が **2 倍**（−0.0140 → −0.0280）、
R² が 0.710 → **0.960** になります。2 つの独立したスイープで同じことが
起きたので、これはこの軸の性質です。

**loss 軸の床つきフィットは `(unconstrained)` です。** L∞ がスキャン上端に
張り付いており、`−0.4900` は推定値ではなく **|b| の下限**として読んでください。
原因は上位 4 セル（2.9297〜2.9496）がほぼ平坦なことで、README が予告していた
「平坦な尾が複数あると床が同定できない」がそのまま起きました。ngram 側は
平坦な尾が 1 点だけだったので `at_boundary: false` でした。

### D≈80 万行で頭打ちになります

この予算（614 万例）では **D = 807,680 行で loss がほぼ底**を打ち、その先
（2.4M / 7.7M / 674M）は 2.93〜2.95 で横ばいです。**より多くのユニークデータを
与えても loss は改善しません。**

ただし **`1 − MRR` 軸は違う**ことを言っています。MRR は D=7,732,879 の
`d100k` で最良（0.5102）で、`d10k`（0.4881）より明確に上です。loss が
飽和したあともランキング性能は伸びており、`benchmark_scaling/` で
「loss 軸の天井が法則を隠していた」のと同じ構図です。**どちらの軸を見るかで
「必要なデータ量」の答えが 10 倍変わります。**

### 過学習は ngram より激しく、ほぼ単調です

best 後の上昇は +1.38 / +1.75 / +0.96 / +0.18 / +0.11 / 0.00 / +0.07 / +0.04。
D が大きいほど小さくなる傾向は明確ですが、**最小の `d100`（+1.38）が
`d300`（+1.75）より小さい**という乱れが 1 点あります。D=8,500 は 1 パスが
33 step しかなく、最良点が step 500（15 パス目）と非常に早いので、
その後の 23,500 step で崩壊しきって頭打ちになったものと思われます。
ngram では同じ位置で単調でした。

### ngram との比較

| D | ngram best loss | scratch best loss | 差 |
|---|---|---|---|
| 8,500 | 4.6147 | **3.4253** | −1.19 |
| 83,521 | 4.2043 | **3.1947** | −1.01 |
| 807,680 | 3.8325 | **2.9357** | −0.90 |
| 7,732,879 | 3.6738 | **2.9469** | −0.73 |

**41M の transformer は 268M エントリの参照表より、どの D でも約 1 nat
良い**です。しかも指数はほぼ同じ（−0.0280 対 −0.0339）で、差は主に切片です
— つまりこの範囲では「アーキテクチャが定数分の下駄を履かせる」のであって
「データの効き方が変わる」のではありません。予算が違う（614 万例 対
1,024 万例）ので厳密な比較ではない点に注意してください。

## モデルサイズ軸との比較

同じコーパス・同じ評価プロトコルで測った 2 つの軸
（モデルサイズ側は `benchmark_scaling/results/chembl/20260827T040036Z_scaling_scratch`、
`scratch-*` 7 サイズ × 48k step）。

| 軸 | y | 主フィット b | R² | 床つき b | 床 L∞ |
|---|---|---|---|---|---|
| モデルサイズ C | valid loss | −0.0214（全点） | 0.759 | −0.1668 | 2.672 |
| モデルサイズ C | 1 − MRR | −0.0307（全点） | 0.689 | −0.4538 *(端)* | 0.4853 |
| **データ量 D**（scratch-medium） | valid loss | **−0.0280**（D 拘束 6 セル） | **0.960** | −0.4900 *(端)* | 2.927 |
| **データ量 D**（scratch-medium） | 1 − MRR | **−0.0237**（D 拘束 6 セル） | **0.954** | −0.1372 | 0.4796 |
| **データ量 D**（ngram） | valid loss | **−0.0339**（D 拘束 7 セル） | **0.980** | −0.1299 | 3.523 |

**同じ教訓が 3 つのスイープで再現しました**: 「効いていない点」を混ぜたまま
単純冪則を引くと −0.01〜−0.02 の平坦な指数が出て、混入源を取り除くと 2 倍
以上急になり R² が跳ね上がります。混入源は軸ごとに違い、モデルサイズ軸では
**曲がるフロンティア**（→ 床つきフィットで対処）、データ軸では
**1 パスに届かないセル**（→ D 拘束フィットで対処）でした。どちらも
「1 つのフィットだけを見ない」という同じ運用に落ちます。

**指数どうしの直接比較はできません。** x 軸の単位が違い（PF-days 対 行数）、
予算も違います。比較できるのは上のような「混入を除くと何倍急になるか」と
「どちらの y 軸で見るか」の水準までです。

**床（L∞）は比較できます。** モデルサイズ軸の 2.672 に対しデータ軸の 2.927。
どちらも `scratch` 系ですが前者は 48k step × 7 サイズ、後者は 24k step で
データを絞ったものなので、**この予算・このデータ量では 2.93 が下限で、
容量とステップを増やせば 2.67 まで下がる**、という読み方になります。

### 次にやるなら

- **`eval_every` を下げる。** 小さい D のセルは最初の評価点が最良で、真の
  最適点が測れていません（ngram の `d100`/`d300`）。指数は浅い側に
  バイアスしています。
- **`max_steps` を上げる。** scratch の `d30k` は最終点が最良（下限値）です。
- **D の刻みを 80 万〜800 万に足す。** scratch の loss はこの区間で頭打ちに
  なるので、飽和点を挟む点が今 2 つしかありません。
- **ランダム標本版の D。** 現状の `max_rows_per_file` は各ファイルの
  先頭 D 行なので「量」と「深さ」が交絡しています（`dall` の異常はこれで
  説明できました）。分離するには行のランダム抽出が要りますが、
  6.74 億行を読み切る必要があるため現実的なコストではありません。
